
**قرارك في محله تماماً، وهذا هو التفكير الهندسي السليم.**

الاندفاع لكتابة كود الطوابق وتعديل الشاشات قبل حسم معمارية النظام بالكامل سيجعلنا نبني فوق "أساس هش" سيتصدع مع أول طابق جديد أو تعديل قادم.

إذا أردنا إجابة صريحة ومباشرة من منظور مهندس برمجيات نظم (Systems Architect):
**المعمارية الحالية بشكلها القائم لا تكفي ولا تناسب فكرة النظام الفضائي متعدد الطوابق والقابل للتوسع.**

إليك تشخيص معماري معمق لما هو ممتاز في الكود الحالي، وما هي **نقاط الاختناق القاتلة (Bottlenecks)**، وكيف نعيد هيكلة المعمارية لتصبح مثل **نواة نظام تشغيل مصغرة (Spatial Micro-Kernel Architecture)**.

---

### 🔍 أولاً: تشخيص المعمارية الحالية (ما لها وما عليها)

#### ✅ النقاط القوية التي يجب الحفاظ عليها:

1. **استقلالية الحزم (Layered Monorepo Packages):** فصل `local_vault_api` (قاعدة البيانات المشفرة محلياً عبر Drift) و `cloud_sync_api` و `voice_ai_api` في مجلد `packages/` كان قراراً ممتازاً يحافظ على استقلالية طبقة البيانات (Offline-First).
2. **إدارة الحالة النظيفة:** استخدام Bloc/Cubit في كل شاشة يوفر مساراً أحادي الاتجاه للبيانات (Unidirectional Data Flow).

#### 🛑 نقاط الاختناق والعيوب المعمارية الحرجة:

#### 1. كائن الإله الاحتكاري (`LauncherRepository` - God Object Anti-Pattern)

* مستودع `LauncherRepository` يتجاوز 1100 سطر، ويقوم **بكل شيء حرفياً**:
  * يدير المهام، المنبهات، المذكرات، جهات الاتصال، فلاش الهاتف، قفل الشاشة، البطارية، الـ GPS، التقاط الكاميرا، استدعاء Gemini، معالجة نصوص الـ TTS، واستماع الميكروفون!
* **المشكلة:** كسر صارخ لمبدأ المسؤولية الواحدة (Single Responsibility Principle). أي إضافة لطابق جديد أو خدمة جديدة تعني حشر مئات الأسطر داخل هذا الملف، وأي عطل فيه سيعطل النظام بأكمله.

#### 2. تشتت الميزة الواحدة (Feature Fracture)

* حالياً، إذا نظرنا لميزة مثل "الأجندة والمهام":
  * واجهتها في الطابق الأرضي موجودة في: `lib/agenda/`
  * واجهتها في الطابق الثاني (الإعدادات) موجودة في: `lib/settings/rooms/settings_agenda_room.dart`
* **المشكلة:** كسر لمفهوم الشريحة الرأسية (Vertical Slice Architecture). الغرفة الواحدة مجزأة ومشتتة بين مجلدين متباعدين، مما يجعل نقلها أو تعديلها أو جعلها موديولاً مستقلاً أمراً معقداً.

#### 3. غياب "الموجّه الفضائي" الحقيقي (Lack of Spatial Router)

* التنقل الحالي ليس نظام توجيه (Router)، بل مجرد شاشة واحدة ضخمة (`SpatialCompassPage`) تحتوي على مصفوفة تحويلات يدوية (`Transform`) مربوطة بمنطق ثنائي ثابت:
  ```dart
  // المعمارية الحالية مبنية على طابقين فقط بنعم/لا:
  bool isSettingsFloor = currentFloor == 1;
  ```
* فيزياء السحب والاحتكاك مطعمة بتفرعات شرطية صلبة:
  `if (direction == center) ... else if (direction == east) ...`
* **المشكلة:** مستحيل إضافة طابق 2 أو طابق -1، ومستحيل إضافة غرفة سادسة دون إعادة كتابة نصف كود ملف `SpatialCompassPage`.

#### 4. توجيه الأوامر الصوتية بالتحقق الصخري الصلب (Rigid Switch Dispatching)

* في `LauncherRepository.dispatchVoiceCommand`، يتم تنفيذ الأوامر عبر عبارة `switch(intent)` صلبة ومطابقة يدوية بالـ Regex.
* **المشكلة:** إذا أضفنا ميزة جديدة في طابق جديد، لا توجد طريقة لتسجيل الأوامر الصوتية تلقائياً (Self-Registering Intents)، بل يجب فتح الـ Repository وتعديل الـ Switch يدوياً.

### 🏗️ ثانياً: المعمارية المستهدفة المقترحة (The Spatial Micro-Kernel Architecture)

لحل هذه المعضلات، سننتقل إلى معمارية **النواة الفضائية وموديولات الغرف المستقلة**:

```
                              ┌────────────────────────────────────────┐
                              │      Spatial Kernel & Router (OS)      │
                              │   (يدير إحداثيات X, Y, Z + فيزياء الحركة) │
                              └───────────────────┬────────────────────┘
                                                  │
                 ┌────────────────────────────────┼──────────────────────────────┐
                 ▼                                ▼                              ▼
    ┌──────────────────────────┐    ┌──────────────────────────┐    ┌──────────────────────────┐
    │  Module: Agenda & Tasks  │    │ Module: Focus & Alarms   │    │  Module: Vision Studio   │
    │  - Ground Widget         │    │ - Ground Widget          │    │  - Ground Widget         │
    │  - Floor 1 Engine Widget │    │ - Floor 1 Engine Widget  │    │  - Floor 1 Engine Widget │
    │  - Domain Repository     │    │ - Domain Repository      │    │  - Domain Repository     │
    │  - Voice Intent Handler  │    │ - Voice Intent Handler   │    │  - Voice Intent Handler  │
    └──────────────────────────┘    └──────────────────────────┘    └──────────────────────────┘
```

#### الركائز الأربع للمعمارية الجديدة:

#### 1. عقد الموديول الفضائي الموحد (`SpatialModule Contract`)

كل ميزة في النظام (الأجندة، المنبه، الكاميرا، الطوارئ) تتحول إلى "حزمة مستقلة بذاتها" (Self-Contained Module) تعرّف نفسها للنظام:

```dart
abstract class SpatialModule {
  String get id;
  String get title;
  IconData get icon;
  
  /// بناء واجهة الميزة بحسب رقم الطابق المطلوب
  Widget buildFloorView(BuildContext context, int floorLevel);
  
  /// الأوامر الصوتية التي يفهمها هذا الموديول
  List<VoiceIntentHandler> get voiceIntents;
  
  /// النغمة الصوتية المميزة للموديول
  SoundCue get sonicSignature;
}
```

* **الفائدة:** صفحة الأجندة أصبحت تجمع شاشة الأرضي وشاشة الإعدادات في نفس المجلد.

#### 2. جدول الطوبولوجيا الفضائية ثلاثي الأبعاد (`SpatialGridTopology`)

بدلاً من حشر كل شيء في كود الشاشة، تصبح الخريطة الفضائية كائناً مستقلاً:

* تعرف الطوابق: `Floors: [-1, 0, 1, 2]`
* تعرف الغرف في كل طابق عبر خريطة اتجاهات:
  ```dart
  topology.register(floor: 0, direction: CompassDirection.north, module: FocusModule());
  topology.register(floor: 1, direction: CompassDirection.north, module: FocusModule()); // يفتح شاشة إعداداتها تلقائياً
  ```
* **الفائدة:** محرك الحركة في الشاشة لا يعرف ما هي "الأجندة" أو "المنبه"؛ هو فقط يحرك الكاميرا بين عقد رياضية `(x, y, z)`.

#### 3. تقسيم الـ Repository الإلهي إلى مستودعات نطاق (Domain Repositories)

نفكك `LauncherRepository` إلى مستودعات أصغر وأكثر نظافة:

* `TaskRepository`: مسؤول فقط عن المهام والمذكرات في Drift و Supabase.
* `HardwareRepository`: مسؤول عن الفلاش، المنبه، البطارية، والتطبيقات.
* `AssistantRepository`: مسؤول عن الـ LLM والـ TTS والـ Speech-to-Text.
* `SettingsRepository`: مسؤول عن تفضيلات النظام والهوية.

#### 4. نظام الملحقات الصوتية (Pluggable Voice Intents)

بدلاً من عبارة `switch(intent)` الضخمة:

* عندما يقول المستخدم: *"اضبط المنبه"*، يسأل المحرك: من من الموديولات المسجلة يدعم `SET_ALARM`؟
* فيجيب موديول `FocusAlarmsModule` ويتولى التنفيذ ذاتياً.

### ⚖️ مقارنة سريعة: قبل وبعد إعادة الهيكلة

| وجه المقارنة                  | المعمارية الحالية                                                            | المعمارية المستهدفة المقترحة                                    |
| :--------------------------------------- | :------------------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------------- |
| **إضافة طابق جديد**   | مستحيل دون إعادة كتابة`SpatialCompassPage` ونظام الـ Transform  | سطر واحد في السجل:`topology.addFloor(2)`                                  |
| **تغيير اتجاه صفحة** | تضارب في النصوص وفيزياء الحركة وأسهم الـ HUD والـ TTS  | نقل اسم الموديول لاتجاه آخر وسيتغير كل شيء آلياً  |
| **تنظيم الكود**          | واجهات الميزة الواحدة مشتتة بين`lib/agenda` و `lib/settings` | شريحة رأسية واحدة تجمع واجهات الميزة بكل طوابقها |
| **حجم `LauncherRepository`**  | ضخم جداً (~1100 سطر) وعرضة للأخطاء                                     | مفكك إلى 4 مستودعات متخصصة عالية الكفاءة                 |
| **الأوامر الصوتية**  | `switch` ضخم مركزي جامد                                                        | نظام`Plugins` تسجل فيه كل غرفة قدراتها الذكية             |

### 🎯 التوصية وخارطة الطريق

أنا **أؤيدك بنسبة 100%**.
الاستمرار في ترقيع الكود القديم دون تعديل المعمارية سيجعل إضافة الطوابق مستقبلاً عملية بطيئة ومحفوفة بالأخطاء.

إذا كنت مستعداً، أقترح أن نسير في **خطة تحول معمارية ذكية (Refactoring Roadmap)** على 3 مراحل لا تكسر عمل التطبيق الحالي:

* **المرحلة 1:** تجميع ملفات كل ميزة معاً في موديول موحد (`Vertical Slices`) وتأسيس عقد `SpatialModule`.
* **المرحلة 2:** تفكيك `LauncherRepository` إلى مستودعات نطاق متخصصة، وتحويل معالجة الصوت إلى نظام موجه ذكي (Intent Registry).
* **المرحلة 3:** بناء **الموجّه الفضائي ثلاثي الأبعاد (`Spatial3DRouter`)** الذي يتعامل مع أي رقم طابق (`int floor`) وأي شبكة غرف بنوابض فيزيائية رياضية نقية.

ما رأيك في هذه الرؤية الهندسية؟ وهل نعتمد خارطة الطريق هذه لنبدأ بإعادة الهيكلة؟
